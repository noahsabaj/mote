# Results — Fedora day one, 2026-08-23

Every number next to its twin (WSL2 = `2026-08-23-chain.md`; Windows-CPU serving = `2026-08-23-prefix-cache.md`).
Machine: Fedora 44, RTX 4060 Ti 8 GB (driver 610.57.04), i7-14700F (**no iGPU** — the desktop holds ~0.72 GiB
of VRAM whenever a session is logged in), root Btrfs zstd:1 on the NVMe. Raw files in `2026-08-23-fedora-day1/`.

## Training step (profile_step, trained router where the twin had one)

| config | Fedora | WSL2 twin | delta |
|---|---|---|---|
| 35M local, 2048, b4, accum 4 | **90.7 KB/s · 26.4 % MFU · 2.7 GB** | 80.8 KB/s · 23.5 % · 2.70 GB | **+12 %** |
| flagship, 8192, b1, ckpt-main | **47.2 KB/s · 35.2 % MFU · 4.1 GB** | 42.3 KB/s · 31.6 % · 4.17 GB | **+11.5 %** |
| flagship, 16384, b1, ckpt-main | **OOM beside the desktop** (needs ~7.1 GiB total; 6.9 available) | 42.4 KB/s · 43.7 % · 6.34 GB | see below |

The 16384 run needs ~6.4 GiB of tensors + ~0.7 GiB CUDA context/Triton; the logged-in desktop leaves 6.9.
WSL2 "fit" because Windows' WDDM pages other apps' VRAM out; native Linux does not. **The flagship pretrain
runs headless** (systemd + linger already survives logout). Estimated 16384 throughput from the +11–12 %
pattern: ~47 KB/s → **~2.4 days per pass** over the 9.9 GB mix (was ~2.7).

## Where the time goes (torch profiler, flagship 8192; 35M 2048 agrees)

* `aten::mul` 16.7 % + `aten::copy_` 13.0 % + `aten::to` dtype churn 9.0 % ≈ **39 % of GPU time** in
  elementwise/precision traffic (the fp32 residual + RMSNorm policy) — GEMMs are only ~22 %.
* **Multi-byte head: 8–13 % of GPU time + 224 MB of saved activations** (block-local attention) — and Muon
  already erased its loss benefit (mbp2 1.774 vs 1.775). Removing it is the cheapest big win.
* Mamba-3 kernels ~7.5 %, FlashRelation backward ~4 %.
* Peak-memory sites (partial event window, proportions): Linear saved activations 620 MB, custom-autograd
  saved tensors 516 MB, RMSNorm fp32 saves ~630 MB, MBP 224 MB.
* The first nsys pass was contaminated by profile_step's own torch-profiler section (66 % "elementwise" and
  88 % sync API time are its overhead); re-trace with the in-script profiler disabled before kernel work.

## Serving (35M, studio on cuda; Windows-CPU twins in brackets)

* Steady state: **cold read ~150 ms at ~1.9 KB [2 100–3 500 ms] · warm 12–45 ms [127] · regenerate 27 ms [55]**;
  decode ~130 B/s [40] — batch-1 byte steps are launch-bound. A fresh server pays ~3 s of Triton JIT on its
  first request (a whole fresh process pays ~37 s across all shapes; the Triton disk cache absorbs most of it after).
* Prefix probe on CUDA (20 greedy turns): **95.8 % reuse, 0 moved cuts, all replies identical** — but
  **max Δlogit 0.03–0.15 per turn** (kernel prefill vs reference continuation; CPU twin was 1.5e-4).
  Usable today; wiring `Input_States` into the kernel path is now measured-priority #1.

## Sharing the card (the baseline the resident daemon must beat)

35M training profile + studio serving simultaneously: warm replies **21–48 ms** and the trainer ran at
**92.2 KB/s / 26.7 % MFU — zero slowdown** (idle twin 90.7 / 26.4). At this scale the serving contract
(first byte ≤ 1 s while training) is met 40× over by two plain processes. The daemon's case is the
flagship regime: no VRAM for two model copies at 16384, and a 44 %-busy GPU with longer kernels.

## Disk

Cold sequential read of the 2.8 GB shard: **4.1 GB/s** (USB-disk source: 389 MiB/s). Training never
needed it, everything else did.

## Follow-ups ranked by today's evidence

1. Drop the multi-byte head from the flagship config (8–13 % time, 224 MB, no loss benefit under Muon).
2. Fuse the norm/residual precision chain (≈39 % of GPU time is elementwise/dtype traffic).
3. `Input_States` through the Mamba-3 kernel for warm continuations (Δlogit 0.148 → exactness).
4. Clean nsys re-trace (add a --no-profiler flag to profile_step first).
5. Rerun the memory snapshot with a bigger event buffer for absolute (not proportional) site totals.
6. Flagship 16384: measure for real from a logged-out session before the pretrain starts.
